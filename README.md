# SayToPay

Type what you want to buy in one sentence. SayToPay turns natural language into a structured order draft, lets you review it, and completes a real **PayPal sandbox** payment — create order → approve → capture — with the transaction ID as proof.

Built for the PayPal AI Hackathon 2026. Category: AI Shopping Assistant / Agentic Commerce.

## How it works

1. **Say it** — one sentence, e.g. `2 coffee beans and a notebook`. The home page lists the demo catalog (names and prices, served by `GET /api/catalog`): click an item to start a draft for it, or name several in one sentence. If nothing matches, the app says so next to the input instead of silently showing no draft.
2. **Review and edit the draft** — the app's single AI step converts the sentence into items, quantities and a total. When an LLM API key is configured (see below), a real AI model does this step (`src/llm.js`, `src/aiParse.js`): the model returns only SKUs and quantities, and the draft is rebuilt from the catalog on the server, so the model never sets prices. The client is provider-neutral — OpenAI, Anthropic, Gemini, or any OpenAI-compatible endpoint, chosen by environment variables. If no key is configured, or the model call fails or times out, a deterministic offline rules parser over the demo catalog (`src/parseOrder.js`) produces the draft instead, so the demo always works. The parse response and the draft note say which path produced the draft (`source`). You can then adjust quantities or remove items in the draft table; the server reprices the edited draft from the catalog (`src/draft.js`) — client-supplied prices are never trusted.
3. **Pay with PayPal (sandbox)** — the server rebuilds the draft from the catalog (SKU + quantity only), creates a PayPal Orders v2 order, redirects the buyer to the PayPal approval page, and captures the order on return (`src/paypal.js`, `src/server.js`). On return the app first looks the order up (`GET /api/orders/:id`): an already-completed payment is shown as-is instead of being captured a second time, and an order that was never approved is reported without capturing anything.
4. **Proof** — the result screen shows the order ID, capture ID and amount; the same transaction appears in the PayPal sandbox dashboard.

## Run it

Requirements: Node.js 18+ (no dependencies to install).

```bash
# 1. Create a Sandbox app at https://developer.paypal.com/dashboard/
#    and copy its Client ID and Secret into a local .env file
#    (see .env.example; .env is git-ignored and is loaded automatically
#    at startup — shell exports still take precedence).
#    Or export them instead:
export PAYPAL_CLIENT_ID=your-sandbox-client-id
export PAYPAL_CLIENT_SECRET=your-sandbox-secret

# 2. (Optional) Turn on the real AI model for the language step by
#    setting any ONE provider key (also via .env):
export OPENAI_API_KEY=your-key        # or ANTHROPIC_API_KEY,
#    GEMINI_API_KEY, or LLM_API_KEY with LLM_PROVIDER / LLM_API_BASE
#    for an OpenAI-compatible endpoint. LLM_MODEL overrides the model.
#    With no key, the built-in rules parser handles every sentence.

# 3. Start
npm start
# -> http://localhost:3000
```

Without credentials the UI still runs and the order-draft step works; the payment endpoints return `paypal_credentials_missing` with setup instructions. **Sandbox only** — no real money moves. Do not set `PAYPAL_ENV=live` for the hackathon demo.

## Demo walkthrough (under 3 minutes)

1. Type `2 coffee beans and a notebook` and click **Build order draft**.
2. Review the draft: Coffee beans 1kg ×2 ($36.00) + Paper notebook ×1 ($9.50) = **$45.50**. Quantities are editable and items removable; the server recalculates the total from the catalog.
3. Click **Pay with PayPal (sandbox)**, approve with a sandbox buyer account, and return.
4. The result screen shows the order ID, capture ID and `COMPLETED` status — the same transaction appears in the PayPal sandbox dashboard.

## Test

```bash
npm test
```

The test suite (91 tests) covers the AI language step (provider
configuration from environment variables, reply validation for the
OpenAI, Anthropic, and Gemini response shapes, catalog repricing of
model output, and fallback to the rules parser on failure, garbage
replies, and timeouts — all with mocked model responses and a local
stand-in endpoint, so no real API key is needed), the natural-language parser
(including group words — "a pair of headphones" and "a couple of
mugs" draft two, "two pairs" drafts four, and "a couple of dozen
mugs" drafts twenty-four — container words: "3 boxes of candles"
drafts three, "2 sets of headphones" drafts two, and a negated
container ("no boxes of candles") drafts none — number words above twelve — "twenty notebooks" is twenty
notebooks and "twenty-one mugs" is twenty-one, not one — scale words:
"a hundred notebooks" and "a thousand candles" draft the scaled
quantity (clamped to ninety-nine), not one, and "a hundred and five
mugs" drafts the scaled quantity, not just the five — summing repeated mentions of the same item in one sentence —
"a mug and three mugs" is four mugs — dozen quantities: "a dozen
mugs" is twelve mugs, "half a dozen" is six, and the hyphenated
forms count the same — "half-dozen" is six and "two-dozen" is
twenty-four, while "no half a dozen mugs" drafts no mugs — quantities stated
before a catalog adjective: "2 wireless headphones" is two headphones,
"a dozen ceramic mugs" is twelve mugs — and before a general
descriptive adjective (a color, a material, a quality): "2 black
headphones" is two headphones, "a dozen red candles" is twelve
candles, "a pair of black headphones" is two, and "no red mugs"
drafts no mugs — trailing counts written after
the item: "mugs x3" is three mugs and "coffee beans x2" is two, applied
to that item only — and list-style counts after the item: "mugs: 3",
"candles: two", and "mugs (3)" draft those quantities for that item,
while a colon with no count after it invents nothing — and the other
list shorthands after the item: "mugs 3", "mugs - 3", "mugs [3]",
and "mugs = 3"
draft three mugs, while a number glued to a unit ("coffee beans
500g") or a longer number ("mugs 2026", "mugs = 2026") invents nothing —
and a postposed comma count that closes the mention: "mugs, three
of them" and "mugs, 3" draft three mugs, while the count in "mugs,
3 candles" still belongs to the candles — and compound number words
in every trailing form: "mugs: twenty-one" drafts twenty-one, not
twenty, and "mugs (forty two)" drafts forty-two, not one — and dozen
and pair counts in every trailing form: "candles: a dozen" drafts
twelve, "candles: two dozen" drafts twenty-four, "mugs (half a
dozen)" drafts six, "mugs, a dozen of them" drafts twelve, and
"headphones: a pair" drafts two — word-boundary matching:
"booking" does not draft a book and "cupcake" does not draft a mug,
while plurals like "mugs" and "notebooks" still match — and explicit
negation: "no notebook, just 2 coffee beans" drafts only the coffee,
and "a mug, not a candle" drafts only the mug, without the negation
leaking onto the next item — and an "of the" connector between the
quantity and the item: "two of the mugs" is two mugs and "a dozen of
the mugs" is twelve — and "more" between a quantity and the item:
"two more mugs" is two mugs, "a dozen more mugs" is twelve, and
"no more mugs" drafts no mugs), the
public catalog listing (names and prices only — parser keywords never
leak), the
server-side draft repricing (a price-tampered draft is corrected to the
catalog total before payment), the `.env` loader, the order status
lookup across CREATED → APPROVED → COMPLETED, and a full create →
approve → capture run
against a local stand-in for the PayPal API (same app code,
`PAYPAL_API_BASE` pointed at the stand-in), including the refusal to
capture before approval. Malformed JSON request bodies are answered
with `400 invalid_json`, not a misleading `502 upstream_error`.

## Layout

- `src/aiParse.js` — the language step: LLM first when a key is configured, rules parser as fallback; reports which path produced the draft
- `src/llm.js` — provider-neutral LLM client (OpenAI / Anthropic / Gemini / OpenAI-compatible), configured by environment variables only
- `src/parseOrder.js` — deterministic offline rules parser (no-key path and fallback)
- `src/draft.js` — server-side repricing of an edited draft from the catalog
- `src/catalog.js` — demo catalog with fixed USD prices, plus its public view for the UI (`GET /api/catalog`)
- `src/paypal.js` — PayPal Orders v2 client (token, create, capture)
- `src/env.js` — dependency-free `.env` loader (shell exports win)
- `src/server.js` — HTTP server and API endpoints
- `public/` — the single-page demo UI
- `test/` — parser tests and the end-to-end flow test
